## 2. 순수 통합 API 계약 (실제 저장소 미연결)

| 함수 | 목적 | 필수 보호 조건 |
|---|---|---|
| \`readProfileView\` | 단일 대상 검색·날짜 필터와 7/30일 요약 | 명시적 프로필 ID 없으면 실패. 검색은 같은 프로필의 요약을 변경하지 않음 |
| \`createProfileRecord\` | 기록 신규 추가 | 동일 ID 중복/전체 20건 초과 거부 |
| \`changeProfileRecord\` | 같은 대상의 기존 기록 수정 | 수정 전 원본 스냅샷과 최신 객체가 동일한지 비교 후 허용 |
| \`deleteProfileRecord\` | 같은 대상 기록 삭제 | 원본 스냅샷 확인, 다른 대상자 기록 삭제 거부 |
| \`exportProfileBackup\` | 선택된 대상만 담은 전용 백업 객체 생성 | 다른 대상·미분류 기록 0건 포함, 기본적으로 평문이므로 별도 암호화 검증 전 공개 사용 금지 |
| \`planProfileImport\` | 전용 백업 파일 복원 사전검사(Preflight) | 같은 \`sourceProfileId\`만 허용, 기록 ID 중복/다른 대상 충돌/20건 한도 차단. 어떠한 기록도 저장하지 않음 |
| \`commitProfileImport\` | 승인 후 **메모리의 새 결과 객체** 생성 | \`confirmed === true\`와 사전검사 당시 원본·백업이 그대로인지 확인. 브라우저/DB 저장은 별도 승인된 트랜잭션 필요 |
| \`createProfileConsultText\` | 단일 대상 진료 요약 텍스트 생성 | 다른 대상 질문·메모·미분류 내용 제외 |

**중요:** \`commitProfileImport\`의 'commit'은 이 모듈에서 **새 자바스크립트 객체를 반환한다**는 의미다. IndexedDB 트랜잭션/서버 커밋/기기 내 저장을 수행하지 않는다. 다른 탭과의 원자적 충돌 방지는 미해결이다.

### 3. 대상자별 전용 JSON의 호환성 경계

전용 형식:

\`\`\`json
{
  "format": "apuda-memory-scoped-backup-v1",
  "version": 1,
  "sourceProfileId": "e4ad61f3-4cf2-40a8-a38c-1d098c91d643",
  "entries": [
    {"id":"A-1","date":"2026-11-12","text":"합성 테스트 관찰"}
  ]
}
\`\`\`

- 예시는 **가상 기록**이다. 실제 개인정보가 담긴 백업 파일을 GitHub에 올리거나 QA에 사용하지 않는다.
- 기존 전체 기록용 \`apuda-memory-care-diary\` **V1/V2**와 전용 형식을 의도적으로 다르게 한다. 구형 JSON을 새 전용 데이터로 자동 변환하거나 현재 대상자에게 자동 배정하지 않는다.
- \`sourceProfileId\`가 선택한 대상과 다르면 가져오기를 거부한다. 다른 브라우저/기기로 동일 ID의 프로필을 안전하게 이식하는 흐름은 **아직 설계·검증하지 않았다.**
- 아직 전용 백업은 **암호화되지 않은 객체**다. 8단계 AES-GCM 프로토타입은 현 사용자 UI에 연결되지 않는다. 암호화된 의료기록 백업을 지원한다고 홍보하면 안 된다.
- 백업 후보의 허용 필드를 제한하고 모르는 필드를 거부한다. 지원하지 않는 필드를 조용히 버리며 복원하지 않는다.
- 검사 중 메모리에 저장하는 원본 상태·백업 문자열은 민감정보를 담을 수 있으므로 장기 보관·로그 출력·서버 전송하지 않아야 한다.

## 4. 합성 데이터 회귀검사 결과

검사 대상: \`tests/memory/test_profile_workflow.mjs\`. 실제 소스 기반 JS 실행으로 다음 항목 **PASS**:

1. A의 검색 결과·7일 요약·진료 질문에 B/미분류 데이터 없음.
2. B의 검색·요약에 A/미분류 데이터 없음.
3. 검색 결과가 0건이어도 해당 대상자의 30일 요약은 독립적으로 정확하게 유지.
4. 명시적 프로필 ID 누락·잘못된 기간·잘못된 검색/날짜 조건 거부.
5. A 프로필 권한으로 B 기록 수정·삭제 거부.
6. A의 수정 전 원본 불일치(다른 변경 발생) 시 덮어쓰기 거부.
7. A의 수정·삭제 완료 결과에서 B 기록 및 미분류 기록 불변.
8. A의 전용 백업에 A 기록만 포함, B·미분류 내용 0건.
9. B 백업을 A에 복원하거나 구형 전체 기록용 V1/V2 JSON을 대상자 전용 형식으로 복원하려는 시도 거부.
10. 사전검사 이후 원본 볼트가 달라지거나 백업이 변경되면 적용 거부.
11. 동일 프로필의 동일 ID·동일 내용은 중복 추가 없이 건너뛰기.
12. 동일 ID가 미분류 또는 다른 대상자에 있으면 충돌로 차단.
13. 중복 ID/알 수 없는 필드/잘못된 날짜 거부.
14. 전체 저장 기록 20건 도달 시 신규 가져오기 차단.
15. 메모리 사전검사·변경 결과가 기존 원본 기록/대상 분리 상태를 직접 변경하지 않음.
16. 선택한 대상의 진료용 텍스트에서 다른 대상의 질문·메모 제외.

검증 환경은 **실제 사용자 정보를 사용하지 않은 독립 JS 로직 시험**이다. 실제 Chrome/Safari의 브라우저 저장·동시 수정·클립보드·인쇄·파일 다운로드·복원 성공 여부는 NT(Not Tested).

## 5. 무손실 통합을 위한 후속 설계 게이트

**A. 사용자 동의 및 데이터 보전**
1. 기존 \`localStorage\` 원본 기록을 어떤 사용자에게도 자동 배정하지 않는다. 현재 데이터는 '미분류'로 보존해야 하며, 검토 전 대상자별 요약에 합산하면 안 된다.
2. 기존 JSON V1/V2를 실제로 사용해 복원/변환하는 시험은 사용자 요청대로 **보류**. 기존 원본 백업 파일의 실재·열람 검증 없이 DB 교체 금지.
3. 대상자별 저장 경로를 적용하기 전에, 단일 기록 수준의 명시적 대상자 검토·취소·되돌리기·복원 내역 기록과 전체 건수 검증 요구.

**B. 저장소·동시성**
1. 실제 IndexedDB 트랜잭션, \`versionchange\`, 동시 2개 탭, 브라우저 중단·쿼터 부족에 대한 원자성 검증.
2. 전체 20건 상한을 유지하는 동안 기록이 많아질 때 백업 유효성 확인·보존기간·데이터 파기 정책 마련.
3. IndexedDB에 전환하더라도 원본 \`localStorage\`는 사용자와 테스트 게이트의 별도 승인 전 자동 삭제 금지.

**C. 개인정보·임상 안전**
1. 익명 UUID와 프로필 분리는 접근통제·암호화를 대체하지 않는다. 같은 브라우저 프로필에서 모든 평문을 읽을 수 있는 구조가 남는다.
2. AES-GCM/PBKDF2 프로토타입의 모바일 기기 성능·비밀번호 분실·암호화 백업 반출 및 독립 보안 검토를 마친 뒤에만 사용자용 내보내기 버튼 연결.
3. 의료기록·진단/처방 지시로 오해하지 않도록 관찰 기록·미기록·진료 질문의 의미를 검증. 외부 전문가 감수와 보호자 실사용성 시험 필요.
4. 유출·잘못된 대상 분류 시 절차와 개인정보 영향평가 기록 필요.

**D. 출시 차단**
- \`docs/qa/apuda-memory-release-gates.json\`의 조건은 여전히 **NO_GO**. 가상 30인단 리뷰의 R01·R02 위험을 출시 가능한 수준으로 해소하지 않았다.
- PR #293은 Draft 유지, 운영 배포/병합 없음. 이번 코드는 기존 사용자 화면의 기존 기록 저장·검색·수정·삭제 동작을 변경하지 않는다.
- 채팅의 '다음'은 개발과 검증 단계 계속 진행이라는 의미이며 운영 배포 승인 또는 실제 환자 기록 이전 승인으로 간주하지 않는다.
