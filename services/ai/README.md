# ApuDa AI Input Service

CPU-oriented AI input service for the ApuDa Health OS.

## Responsibilities

- OCR of uploaded lab-result images
- Korean speech-to-text for short symptom notes
- deterministic symptom/lab parsing
- Redis-backed background jobs
- automatic temporary-file deletion
- user confirmation before parsed results are written to the Health OS database

## API

- `GET /health`
- `POST /api/v1/ocr`
- `POST /api/v1/stt`
- `POST /api/v1/parse/lab`
- `POST /api/v1/parse/symptom`
- `GET /api/v1/jobs/{job_id}`

Health-data job endpoints require the server-only API secret plus an opaque per-user owner token generated by the ApuDa web server:

```text
X-ApuDa-AI-Key: <server secret>
X-ApuDa-Owner: <HMAC owner token>
```

The owner token is stored only as job metadata and prevents one signed-in ApuDa user from polling another user's OCR/STT result if a job ID were exposed.

The browser must never receive `APUDA_AI_API_KEY`. Browser uploads go to the authenticated Next.js routes under `/api/ai/*`, which proxy requests server-to-server.

## VPS deployment target

Designed for the CPU-only ApuDa VPS.

Initial configuration:

- one RQ worker
- faster-whisper `small` / `int8`
- 2 CPU threads
- VAD enabled
- OCR/STT models lazily loaded and reused in the worker process
- API bound to `127.0.0.1:8000`
- Redis available only on the internal Docker network
- Caddy/Nginx terminates HTTPS when a remote app host must reach the AI service

These are initial settings, not performance guarantees. Benchmark OCR/STT latency and RAM/CPU before increasing concurrency.

## Start

```bash
cp .env.example .env
# Replace APUDA_AI_API_KEY with a long random secret.
./deploy-vps.sh
```

Manual equivalent:

```bash
docker compose up -d --build
docker compose ps
curl http://127.0.0.1:8000/health
```

## Privacy and lifecycle

Do not log raw OCR text, transcripts, names, diagnoses, lab values, symptoms, audio, or uploaded images.

Uploads are deleted by the worker after processing. If enqueueing fails, the just-uploaded temporary file is deleted as well. Job results are short-lived in Redis and should only be persisted to the Health OS after the user reviews and confirms them.

The public health endpoint checks Redis connectivity, so container health does not report healthy when the queue backend is unavailable.
